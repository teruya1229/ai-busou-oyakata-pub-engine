# handoff

## 次にやるべき1手
- 4コマ1枚画像の作成本番導線を決める：外部画像生成API・手動エクスポートのどちらを先に繋ぐかを1点に絞る
- 方針が「API」なら、`comicUnifiedPrompt`（または応答の画像URL）を既存プレビュー欄へ渡す最小配線だけから着手する

## 判断基準
- まず画面上で「生成結果の画像」を確実に見たいなら、今回追加済みのプレビューへ URL / data URL を流し込む方式で十分かを確認する
- プロンプト文面の改善が先なら、`js/engine.js` の `buildUnifiedComicImagePrompt` 周辺のみ最小差分で調整する（API実装はまだ不要）
- どちらを選ぶ場合も、既存の 4コマ / note / X / Kindle 各導線と `js/kindle-engine.js` を壊さないことを優先する

## 今回やらないこと
- 永続化（保存/履歴）
- 外部AI API の本格接続（画像生成サービスの選定・認証・エラー処理の一式）
- Kindle用出力ロジックの変更
- 複数画面化や高度なUI演出

## 実装方針
- ルールベースを維持し、Kindle責務は `js/kindle-engine.js` に寄せて拡張する
- 既存MVP本体（`engine.js` / `templates.js`）は必要時以外触らず、影響範囲を限定する
- UI変更が必要な場合でも、既存導線への「追加」方式で最小差分にとどめる

## 注意点
- 既存MVP本体の仕様変更や大規模リファクタリングは行わない
- Kindle責務は `js/kindle-engine.js` に寄せる（今回のプレビュー追加は Kindle に無関係）
- `chapter-episodes` 再利用方針を崩さない
- 4コマ画像プレビューは `http(s)://` と `data:image/...` のみ許可している（`javascript:` 等は拒否）

## 次の拡張候補
- 画像生成API応答（URL または base64）をプレビューへ自動反映する最小配線
- 現場ジャンル別テンプレ（内装/設備/外構など）
- 文字数制約を考慮したX投稿最適化
- 出力プリセット（朝礼向け/振り返り向け）
- 将来のAPI差し替えポイントのインターフェース化
