# handoff

## 次にやるべき1手
- 完成原稿寄り（manuscript preview）を基点に、見え方調整へ進むか、Kindle導線をMVP区切りとして整理するかを1つに絞って判断する。

## 判断基準
- 1入力で3出力が破綻なく出ること
- トーン選択が文体に反映されること
- 読んだときに「最後の小さな学び」が明確であること
- テーマ未入力や短文入力でも不自然な空欄が出ないこと
- 代表ケースで `expectedPattern` と実出力の意図が概ね一致すること
- 評価結果を `docs/evaluation-log.md` に追記し、前回との差分が説明できること
- `TC-04` と `TC-08` の改善が他ケースを崩していないこと
- 次回修正後に `TC-06` `TC-07` `TC-05` のpattern整合が改善していること
- 次回は pattern を崩さず、学びの自然さ調整を最小差分で行えること
- `TC-03` `TC-06` のX長文改善が他ケースの文面を劣化させていないこと
- 全8ケースの最終点検で、MVPを一旦固定可能と判断できること
- `docs/kindle-bridge-design.md` の粒度定義（1エピソード/1節/1章）で実例が無理なく割り当てられること
- `docs/chapter-mapping-examples.md` の試作で、章タイトル/節タイトル/本文素材の接続が破綻しないこと
- `docs/kindle-chapter-template.md` の固定ルールで、章/節テンプレが運用可能なこと
- `docs/sample-kindle-chapter-outline.md` で、導入->4節->まとめの流れが実務的に自然であること
- `docs/kindle-drafting-rules-v1.md` の粒度定義で、本文試作時に長さと読み味の比較が可能であること
- `docs/sample-section-drafts.md` の比較で、標準粒度を第一候補として合理的に説明できること
- `docs/kindle-granularity-policy-v1.md` の配分方針（標準4を基本）で章構成が無理なく成立すること
- `docs/sample-kindle-chapter-draft-v1.md` で、章導入->4節->章末まとめの接続が自然であること
- 微修正後ルールで、標準粒度の節が4〜6段落に収まり、冗長化を抑えられていること
- 節末要点の文末スタイルが「〜する。」で統一され、章内で混在しないこと
- `docs/sample-section-draft-v2.md` で、前回比の読みやすさ改善が説明可能であること
- `docs/sample-kindle-chapter-draft-v2.md` で、4節通しでも読み味と運用性が維持できること
- 最終固定判断で、固定項目と保留項目が明確に分離されていること
- `docs/kindle-generation-rules-v1.md` で、入力から章素材までの責務分離が実装可能な粒度で整理されていること
- `docs/kindle-implementation-plan-v1.md` で、入力/中間構造/節素材/章素材のデータ境界が明確なこと
- `js/kindle-engine.js` で、1エピソード -> Kindle節素材オブジェクトが安定して生成できること
- 単一入力を `[input]` として渡し、`Kindle章素材プレビュー` がUIで確認できること
- `---` 区切り複数入力から、`buildKindleChapterPreview(inputs)` で章素材が確認できること
- `---` 区切り複数入力から、`buildKindleBookPreview([episodes])` で本素材プレビューが確認できること
- 既存の単一入力導線・章確認導線・3出力導線を壊さずに追加表示できること
- `===` 区切りで複数章、`---` 区切りで章内エピソードを扱い、`buildKindleBookPreview([[chapter1], [chapter2], ...])` で本素材確認できること
- `===` が無い従来入力でも、後方互換として1章ぶんの本素材確認ができること
- `chapter-episodes` を再利用し、`buildKindleDraftOutlinePreview(chapters)` で本文骨子確認ができること
- 本文骨子確認導線追加後も、既存の 4コマ / note / X / Kindle節 / Kindle章 / Kindle本 の表示導線が壊れていないこと
- `chapter-episodes` を再利用し、`buildKindleChapterDraftsPreview(chapters)` で章本文たたき台確認ができること
- 章本文たたき台確認導線追加後も、既存の section / chapter / book / draft outline 導線が壊れていないこと
- `chapter-episodes` を再利用し、`buildKindleFullDraftPreview(chapters)` で全体原稿たたき台確認ができること
- 全体原稿たたき台確認導線追加後も、既存の section / chapter / book / draft outline / chapter drafts 導線が壊れていないこと
- `chapter-episodes` を再利用し、`buildKindleManuscriptPreview(chapters)` で完成原稿寄り確認ができること
- 完成原稿寄り確認導線追加後も、既存の section / chapter / book / draft outline / chapter drafts / full draft 導線が壊れていないこと

## 今回やらないこと
- 永続化（保存/履歴）
- 外部AI API接続
- Kindle用出力
- 複数画面化や高度なUI演出

## 実装方針
- ルールベースを維持し、`engine.js` の関数を拡張していく
- 変更多発を避けるため、`templates.js` 側で文言差分を吸収する
- `app.js` はUIイベントと表示に限定する

## 注意点
- 静的構成を維持し、buildツールを導入しない
- UTF-8前提で文字化けを避ける
- 1画面完結UIのまま、過剰機能を入れない
- `templates.js` と `engine.js` を中心に最小差分で改善する
- 調整前に評価ケースを固定し、感覚修正だけで進めない
- 修正対象は fail/要確認ケースに限定し、正常ケースを不用意に触らない
- 修正後は `docs/evaluation-log.md` の判定とmemoを必ず更新する
- 修正対象は最大3件に固定し、横展開リファクタをしない
- pattern整合を直した箇所へ追加変更する際は、対象ケース以外の回帰確認を必ず先に行う
- X長文調整時は `buildXPost()` の局所変更に留め、4コマ / note へ変更を波及させない
- 次フェーズでは実装前に設計メモを先に確定し、MVP固定版を不用意に崩さない
- Kindle実装（自動生成/EPUB/保存機能）には入らず、前段設計の妥当性確認に限定する
- 章テンプレ具体化まではドキュメント運用に限定し、コード改修に入らない
- 章テンプレ固定後も、原稿生成ルール確定までは実装着手しない
- 実例原稿構成の検証段階では、文学的な表現最適化より運用可能性を優先する
- 本文試作フェーズでもMVP本体コードには触れず、まずはドキュメント検証を優先する
- 標準粒度固定までは、節本文の文体拡張より文字量と構成の再現性を優先する
- 粒度方針確定後の本文試作でも、例外ルールを増やしすぎない
- 本文見直し時も、章構成の安定性を優先し、過度な表現最適化を避ける
- 微修正ルール適用時は、段落上限・節末要点1文・導入同型化回避の3点を優先確認する
- 1章再試作へ進む判断時は、1節単位の改善差が再現可能かを先に確認する
- 最終固定判断は、章全体での段落密度と節間の重複感をあわせて確認する
- 次フェーズでは保留項目（章導入長さ上限・語彙差ガイド）以外を再変更しない
- 次フェーズでもMVP本体コードは触らず、まずは量産試作か実装設計のどちらか1本に絞る
- 実装着手時も、まずは節素材/章素材の最小生成までに範囲を限定する
- Kindle実装時も既存の 4コマ / note / X 出力は置き換えず、再利用ベースで拡張する
- 複数入力導線を足す場合も、既存の単一入力生成導線は変更せず追加方式を維持する
- 複数入力改善時も、動的フォーム化など大きなUI変更は避ける
- 本素材プレビュー段階では複数章入力UIを増やさず、まず既存 `chapter-episodes` 再利用を維持する
- 章確認導線は従来どおり維持し、本確認導線だけを段階的に改善して影響範囲を限定する
- 本文骨子確認でも新規入力UIは追加せず、既存の `chapter-episodes` のみを使う
- 次フェーズで章本文生成に進む場合も、まずは `js/kindle-engine.js` への小さな追加で完結する範囲に限定する
- 章本文たたき台確認でも新規入力UIは追加せず、既存の `chapter-episodes` のみを使う
- 次フェーズで全体原稿たたき台生成に進む場合も、`introDraft / chapterDrafts / closingDraft` の既存構造再利用を優先する
- 全体原稿たたき台確認でも新規入力UIは追加せず、既存の `chapter-episodes` のみを使う
- 次フェーズで完成原稿寄りへ進む場合も、まずは `js/kindle-engine.js` への最小追加で整形責務を限定する
- 完成原稿寄り確認でも新規入力UIは追加せず、既存の `chapter-episodes` のみを使う
- 次フェーズで見え方調整する場合も、`js/kindle-engine.js` の最小調整に限定し既存UI導線は維持する
