# handoff

## 次にやるべき1手
- **外部画像生成の戻り値形式を1つ決める**（返るのが **HTTPSの画像URL** か、**base64 / data URL** か）
- 形式が決まったら、`js/app.js` に **fetch + プレビュー反映の薄いアダプター**（数行〜数十行）だけ置き、UIの「生成結果」欄へ結果を流し込むところから着手する
- 着手前に **どのサービスで試すか** を1つに絞り、無理に抽象化しない

## 判断基準
- **まだ手運用で足りる**なら、今回の「転記＋貼り付けプレビュー」で一区切りにしてよい
- **毎回コピペが負担**なら、API・またはローカルスクリプトから **生成結果だけ** を `comic-image-url` 相当へ入れる最小配線が最も費用対効果が高い
- **共通**：4コマ / note / X / Kindle 既存導線と `js/kindle-engine.js` を壊さないこと。Kindle責務に触れないこと

## 今回やらないこと
- 永続化（保存/履歴）
- 外部AI API の本格実装（認証・レート制限・リトライ設計の一式）
- Kindle用出力ロジックの変更
- 複数画面化や高度なUI演出

## 実装方針
- ルールベースを維持し、Kindle責務は `js/kindle-engine.js` に寄せて拡張する
- 既存MVP本体（`engine.js` / `templates.js`）は必要時以外触らず、影響範囲を限定する
- UI変更が必要な場合でも、既存導線への「追加」方式で最小差分にとどめる

## 注意点
- 既存MVP本体の仕様変更や大規模リファクタリングは行わない
- Kindle責務は `js/kindle-engine.js` に寄せる
- `chapter-episodes` 再利用方針を崩さない
- 4コマ画像プレビューは `http(s)://` と `data:image/...` のみ許可（`javascript:` 等は拒否）。API接続時もこの制約を崩さない

## 次の拡張候補
- 生成APIのレスポンス→ `生成結果（画像URL / data URL）` への自動投入（または `img.src` 直指定の最小経路）
- ファイルアップロード／ローカル画像のプレビュー（File API）
- 現場ジャンル別テンプレ（内装/設備/外構など）
- 文字数制約を考慮したX投稿最適化
