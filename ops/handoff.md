## 次にやるべき1手
- chapter mapping の結果をもとに粒度（1エピソード/1節、3〜4節/1章）を確定する。

## 判断基準
- 1入力で3出力が破綻なく出ること
- トーン選択が文体に反映されること
- 読んだときに「最後の小さな学び」が明確であること
- テーマ未入力や短文入力でも不自然な空欄が出ないこと
- 代表ケースで `expectedPattern` と実出力の意図が概ね一致すること
- 評価結果を `docs/evaluation-log.md` に追記し、前回との差分が説明できること
- `TC-04` と `TC-08` の改善が他ケースを崩していないこと
- 次回修正後に `TC-06` `TC-07` `TC-05` のpattern整合が改善していること
- 次回は pattern を崩さず、学びの自然さ調整を最小差分で行えること
- `TC-03` `TC-06` のX長文改善が他ケースの文面を劣化させていないこと
- 全8ケースの最終点検で、MVPを一旦固定可能と判断できること
- `docs/kindle-bridge-design.md` の粒度定義（1エピソード/1節/1章）で実例が無理なく割り当てられること
- `docs/chapter-mapping-examples.md` の試作で、章タイトル/節タイトル/本文素材の接続が破綻しないこと

## 今回やらないこと
- 永続化（保存/履歴）
- 外部AI API接続
- Kindle用出力
- 複数画面化や高度なUI演出

## 実装方針
- ルールベースを維持し、`engine.js` の関数を拡張していく
- 変更多発を避けるため、`templates.js` 側で文言差分を吸収する
- `app.js` はUIイベントと表示に限定する

## 注意点
- 静的構成を維持し、buildツールを導入しない
- UTF-8前提で文字化けを避ける
- 1画面完結UIのまま、過剰機能を入れない
- `templates.js` と `engine.js` を中心に最小差分で改善する
- 調整前に評価ケースを固定し、感覚修正だけで進めない
- 修正対象は fail/要確認ケースに限定し、正常ケースを不用意に触らない
- 修正後は `docs/evaluation-log.md` の判定とmemoを必ず更新する
- 修正対象は最大3件に固定し、横展開リファクタをしない
- pattern整合を直した箇所へ追加変更する際は、対象ケース以外の回帰確認を必ず先に行う
- X長文調整時は `buildXPost()` の局所変更に留め、4コマ / note へ変更を波及させない
- 次フェーズでは実装前に設計メモを先に確定し、MVP固定版を不用意に崩さない
- Kindle実装（自動生成/EPUB/保存機能）には入らず、前段設計の妥当性確認に限定する
- 章テンプレ具体化まではドキュメント運用に限定し、コード改修に入らない
