# handoff

## 次にやるべき1手
- **A と B のどちらを先にするかを1点に絞る**
  - **A)** 統合画像プロンプト（`comicUnifiedPrompt`）から、外部の画像生成フローまで繋ぎ、返った **画像URL / base64** を既存プレビューへ渡す（APIの本格選定・認証はまだ最小でよい）
  - **B)** URL貼り付けに加え、**ファイルアップロードまたはローカル画像** を `data:` / blob URL 経由でプレビューできるようにする
- 選んだ方以外は「今回やらない」に戻し、差分を `index.html` / `js/app.js` 中心に抑える

## 判断基準
- **まず運用で何が詰まるか**で切る：生成後の取り込みが毎回手作業で負担なら A、ローカル素材の確認が主なら B
- **セキュリティと実装コスト**：B は File API とプレビュー排他の最小実装で足りることが多い。A はレスポンス形式（URL かバイナリか）が決まってから着手すると無駄が少ない
- **共通**：既存の 4コマ / note / X / Kindle 各導線と `js/kindle-engine.js` を壊さないこと、Kindle責務に触れないこと

## 今回やらないこと
- 永続化（保存/履歴）
- 外部AI API の本格接続（画像生成サービスの選定・認証・エラー処理の一式）
- Kindle用出力ロジックの変更
- 複数画面化や高度なUI演出

## 実装方針
- ルールベースを維持し、Kindle責務は `js/kindle-engine.js` に寄せて拡張する
- 既存MVP本体（`engine.js` / `templates.js`）は必要時以外触らず、影響範囲を限定する
- UI変更が必要な場合でも、既存導線への「追加」方式で最小差分にとどめる

## 注意点
- 既存MVP本体の仕様変更や大規模リファクタリングは行わない
- Kindle責務は `js/kindle-engine.js` に寄せる（今回のプレビュー追加は Kindle に無関係）
- `chapter-episodes` 再利用方針を崩さない
- 4コマ画像プレビューは `http(s)://` と `data:image/...` のみ許可している（`javascript:` 等は拒否）

## 次の拡張候補
- 画像生成API応答（URL または base64）をプレビューへ自動反映する最小配線
- 現場ジャンル別テンプレ（内装/設備/外構など）
- 文字数制約を考慮したX投稿最適化
- 出力プリセット（朝礼向け/振り返り向け）
- 将来のAPI差し替えポイントのインターフェース化
