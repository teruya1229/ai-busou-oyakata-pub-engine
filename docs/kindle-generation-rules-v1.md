# Kindle生成ルール整理 v1

- **前提（現行MVP）**: 主線は **漫画原稿・8コマ・note**。旧4コマ短縮は互換。**X は主線外**。以下の「4コマ」表記は **旧設計の略称**として、実体は **8コマネーム／`comicLegacy4`** に読み替える。

## 1. このドキュメントの目的
- 固定済みの章テンプレと drafting rules を前提に、将来の Kindle原稿生成へ接続するための生成ルールを整理する。
- 実装前に変換手順と責務を明確化し、`engine.js` へ落とし込みやすい基準を作る。

## 2. なぜ今、量産試作より先に生成ルール整理を行うのか
- 試作のみを先行すると、運用ごとに変換手順がぶれやすい。
- 生成ルールを先に固定すると、量産試作と実装設計を同じ判断軸で進められる。
- 保留項目の影響範囲を限定し、不要な再修正を減らせる。

## 4. 入力として必要な要素
- 現場メモ（何が起きたか）
- 学び（再発防止・改善の核）
- 登場人物（照屋親方 / コパイロット / 班メンバー）
- トーン（語り口の温度感）
- タイトルテーマ（章・節タイトルの方向性）

## 5. 入力から中間構造へ変換するときの考え方
- 入力はまず「事実」「原因」「行動」「学び」に分解する。
- 1入力を1エピソード単位の中間構造へ正規化し、空欄は最小補完で埋める。
- 中間構造は章化前提で、以下キーを持つ。
  - `episodeId`
  - `theme`
  - `incident`
  - `cause`
  - `action`
  - `learning`
  - `tone`
  - `characters`
  - `pattern`

## 6. 中間構造から ネーム・note・X（参考）を作る役割整理
- 8コマネーム（旧 **`comicLegacy4`** は4段短縮）: 導入フック用の場面圧縮（状況 -> ズレ -> 気づき -> 学びのイメージ）。
- note: 節本文骨格（起きたこと -> なぜ -> 学び -> まとめ）。
- X（主線外）: 節末要点1文、章タイトル補助、章導入補助の短文化素材。

## 7. ネーム・note・X から Kindle章素材へ変換するルール
- ネーム（8コマ／旧短縮）は節冒頭の導入フックへ変換し、本文主軸にはしない。
- noteは節本文の主素材として優先採用し、改稿は接続調整に限定する。
- Xは節末要点1文とタイトル補助に限定し、本文への過剰挿入を避ける。
- 章素材変換時は、節ごとに「導入」「本文」「節末要点」を必ずセット化する。

## 8. 1エピソード -> 1節 の生成ルール
- 1入力 = 1節を原則とする。
- 節構成は「本文4段落 + 節末要点1文」を標準とする。
- 節末要点は本文学びを言い換えた1文で、文末は「〜する。」に固定する。
- 導入は同型化回避のため、起点（状況/判断/違和感）を節ごとに回す。

## 9. 複数エピソード -> 1章（4節）の生成ルール
- 同一テーマ群の4エピソードを束ね、1章を構成する。
- 節順は「問題認識 -> 防止 -> 改善 -> 定着」を基本とする。
- 章構成は「章導入 -> 4節 -> 章末まとめ」を固定する。
- 素材不足時のみ3節を例外許容し、無理な水増しはしない。

## 10. 章タイトル生成の考え方
- X短文の主語句 + テーマ語 + 効果語（防ぐ/減らす/整える）で組む。
- 25〜40字を目安に、現場語を1語以上含める。
- 抽象語だけで終わらず、行動イメージが浮かぶ語を入れる。

## 11. 節タイトル生成の考え方
- 「課題 + 行動 + 期待効果」の3要素で生成する。
- 例: 「搬入導線の先共有で詰まりを防ぐ」。
- 同一章内で行動語の重複が続く場合は、動詞を優先的に差し替える。

## 12. 節末要点1文の生成ルール
- 1節につき1文のみ。
- 新情報を追加せず、本文学びを行動単位で再表現する。
- 文末は「〜する。」に統一し、「〜である。」を混在させない。
- X由来表現は節末中心に使い、本文比率は2割以内に抑える。

## 13. 保留項目の扱い
- 章導入文の長さ上限
  - 現時点は可変運用。
  - 量産試作で平均文字量を計測して上限候補を決める。
- 節間語彙差ガイド
  - 現時点は運用判断。
  - 章内で動詞・現場語の重複率を確認し、必要時のみガイド化する。

## 14. 将来、実装時に分離すべき責務
- 入力正規化責務（欠損補完、トーン整形、人物整形）
- 中間構造生成責務（事実/原因/行動/学びの抽出）
- 出力生成責務（原稿・8コマネーム・note／旧短縮・Xは参考）
- Kindle変換責務（節化、章化、タイトル生成、節末要点生成）
- 検証責務（段落数・文末・構成順のルールチェック）

## 15. 今はまだ自動化しないもの
- Kindle本文の自動生成実装
- EPUB出力・自動組版
- 外部API連携・保存機能
- 複雑な例外分岐の自動最適化

## 16. 次フェーズで試すべきこと
- 本ルールで量産試作（複数章）を行い、再現性を確認する。
- 保留項目2点（章導入長さ上限、節間語彙差）だけを対象に検証する。
- 実装設計へ進む場合は、`engine.js` に落とす責務境界を先に確定する。
