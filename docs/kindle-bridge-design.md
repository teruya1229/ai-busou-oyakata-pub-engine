# Kindle橋渡し設計（前段）

- **前提（現行MVP）**: 主線は **漫画原稿・8コマ標準ネーム・note**。旧4コマ短縮は `comicLegacy4`（比較・互換）。**X は主線外**（`buildXPost` は残置）。Kindle章化は **将来の別モード**を想定した前段メモ。

## 1. このドキュメントの目的
- 将来のKindle章へ接続しうる素材（**原稿・8コマネーム・note**、必要に応じ旧短縮・X）を整理するための最小ルールを定義する。
- 実装前に設計を固定し、MVP本体を崩さず次フェーズへ進める判断材料にする。

## 2. なぜ今 Kindle実装ではなく Kindle前段設計を行うのか
- 現時点はMVP固定フェーズであり、出力品質の一貫性確認まで完了しているため。
- いきなり自動組版やEPUB実装に進むと、要件未整理のまま機能が膨らむリスクが高い。
- 先に章構成の接続ルールを明文化することで、次フェーズの実装差分を最小化できる。

## 3. 現行の素材の役割整理（Kindle前段）

### 漫画ネーム（8コマ主線／旧4コマ短縮は別）
- 章の導入フック候補（**8コマ**を要約・抜粋。旧 **`comicLegacy4`** は4段の短縮比較用）。
- または章内のコラム（現場エピソード枠）候補。
- 役割は「状況 -> ズレ -> 気づき -> 小さな学び」の短距離提示（旧4段に相当する圧縮イメージ）。

### note
- Kindle本文素材の主軸。
- 導入、背景、原因、学び、まとめが揃っており、章本文へ転用しやすい。
- 章化では、note構成を節の骨格として扱う。

### X（主線外・参考）
- 章タイトル候補、要点抽出、帯文候補（**現行UIの主線には含めない**。`buildXPost` 等の残置を想定）。
- 章の「ひとこと要約」や販促導線（紹介文）として活用する。
- 長文版は章冒頭のリード文候補にも使える。

## 4. Kindleへの橋渡し方針
- フローは `現場メモ -> 構造化 -> 原稿・8コマネーム・note（必要に応じ旧短縮・X）-> Kindle章` を想定する（**Kindle同時生成は主線に含めない**）。
- 最初のKindle化は「章素材を作れること」を優先し、自動組版は行わない。
- 1エピソード単位で素材を固定し、後段で章に束ねる。

## 5. 1エピソード / 1節 / 1章 の推奨粒度
- 1エピソード: 現場の1出来事（現行の1入力 = 1エピソード）
- 1節: 2〜3エピソードを同テーマで束ねる
- 1章: 2〜3節（合計4〜9エピソード）を目安

## 6. 章構成テンプレ案
- 章タイトル（X短文/長文から候補抽出）
- 章リード（X長文を整形して使用）
- 節1: 代表エピソード（note本文ベース）
- 節2: 追加エピソード（note本文ベース）
- コラム: ネーム要約・抜粋（8コマ主線。旧4段は任意）（導入フック）
- 章まとめ: 共通学び（note「学び」「まとめ」から再編集）

## 7. 現行出力から章へ変換する最小ルール
- ルール1: 章タイトル候補は `X短文版` の先頭行を優先採用する。
- ルール2: 章リード候補は `X長文版` を1〜2文に整形して使う。
- ルール3: 節本文は `note` を原文ベースにし、見出しだけ章構成に合わせる。
- ルール4: ネーム（8コマ／旧短縮）は本文化せず、節冒頭のフックか章内コラムに限定する。
- ルール5: 章末学びは各エピソードの `学び` 行を3点以内で統合する。

## 8. 次フェーズで追加すべき機能候補
- 章マッピング用のメタ情報出力（episodeId / themeGroup / chapterCandidate）
- 章テンプレのプリセット（現場安全、段取り改善、振り返り活用）
- 章リード候補を複数案で出す簡易ルール
- 最終的な原稿整形手順（Markdownベース）ガイド

## 9. 今はまだやらないこと
- Kindle本文自動生成の実装
- EPUB出力
- 自動組版
- 外部API連携
- 保存機能やデータベース導入
